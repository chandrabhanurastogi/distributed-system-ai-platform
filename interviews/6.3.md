## Q1: `OllamaLlmClient` and `GeminiLlmClient` are both selected via `@ConditionalOnProperty(name = "llm.provider", havingValue = "...")`. Your first version used `@Primary` on the Ollama bean instead. Why did `@Primary` fail to actually satisfy this milestone's goal — what would still have been true about the Spring context under `@Primary` that isn't true under `@ConditionalOnProperty`?

**Answer given:** Correctly identified the underlying architecture — under `@Primary`, both beans exist; the annotation only breaks the tie when an unqualified injection point sees two candidates. But named the wrong annotation for the actual fix: said `@EnabledIfEnvironmentVariable` gives "more control without changing the code for choosing the LLM," and described the mechanism as beans being "created only if the environment variable exists."

**Corrections:**
1. `@EnabledIfEnvironmentVariable` is a JUnit 5 *test*-gating annotation — it decides whether to run a test method based on an OS environment variable. It has nothing to do with which Spring beans get created in the running application. The actual annotation is `@ConditionalOnProperty`.
2. `llm.provider` is a Spring *property*, set in `application.yml` — not an OS environment variable. Spring properties can be sourced from env vars too, but that's a separate mechanism, and it's not what's happening here. This distinction mattered concretely earlier in this same milestone, during the `GEMINI_API_KEY` propagation confusion between an IDE run configuration and a plain shell.

**Accepted answer:** `@ConditionalOnProperty` is evaluated at bean-*definition* registration time, before the context is even fully assembled — a non-matching bean's definition is never registered at all, meaning the object never exists in memory. `@Primary` has no equivalent capability; it can only influence which bean an ambiguous unqualified injection point resolves to, never prevent a bean from being created in the first place. `LlmProviderConditionTest`'s `doesNotHaveBean(...)` assertions are proving "does not exist," not "exists but isn't preferred."

## Q2: `GeminiLlmClient.chat()` resends the entire message history via the `input` field on every single call — even though Gemini's real Interactions API supports `previous_interaction_id`, letting the server remember prior turns. What does this decision cost you in a long multi-turn conversation against Gemini specifically, and why did we accept that cost instead of using Gemini's native mechanism?

**Answer given (correct and complete on the first pass):** "With Option C, with the multi-turn conversation the prompt will continue to grow and thus the tokenization process and the cost will grow. The reason we use this approach is to be consistent across both the models Gemini and Ollama. If I were only using Gemini, I would have not used this approach and rather use the Gemini native approach of sharing the previous interaction ID."

No correction needed — this correctly identifies both the cost (monotonically growing input-token spend per turn) and the reason for accepting it (a uniform interface both providers satisfy).

## Q3: You hit two different failures in sequence debugging the real Gemini API — first `x-goog-api-key` header → 401 `ACCESS_TOKEN_TYPE_UNSUPPORTED`, then `Authorization: Bearer` → 403 "unregistered callers." The real root causes turned out to be unrelated to either header format (the Gemini API wasn't enabled on the project, and the model was deprecated). Why couldn't switching the header format alone have fixed either error, and what does that tell you about what a 401 vs. a 403 is actually telling you as a debugging signal, in general?

**Answer given:** "401 means unauthenticated, 403 means authenticated but not authorized. Switching the header format has nothing to do against enablement of Gemini API for the project whose key I was using for authorization. Switching the header may help in authentication part but if the authorization is not given at server side then it can't do much."

**Refinements added:** the standard 401-vs-403 textbook distinction is correct. One precision worth adding: `ACCESS_TOKEN_TYPE_UNSUPPORTED` is a more specific flavor of 401 than "no credentials sent at all" — it means the server saw *some* credential but flagged its type as unrecognized. The broader, generalizable lesson: the fact that changing the header format changed *which flavor* of failure appeared (401 → 403), rather than fixing anything, is itself a signal that the problem is server-side account/project state, not the client-side credential-passing mechanism.

## Q4: Suppose Phase 10 (Agents) later builds a loop calling `LlmClient.chat()` many times in quick succession, each step appending to a growing conversation. Given the statelessness decision from Q2, what specific problem would show up for the Gemini path that would *not* show up for Ollama, purely as a consequence of this interface design — and how would you detect it happening in practice, not just suspect it from reading the code?

**Answer given (first attempt — off-target, but a genuinely new and valuable finding):** Named three real risks in `GeminiLlmClient.serializeMessages()`'s flat-string transcript format: (1) role hallucination — the model has only a trailing `Assistant:` text hint to know when to stop, unlike Ollama's hard `<|eot_id|>` stop token, so a long agent transcript could plausibly continue past its own turn; (2) delimiter bleed — a tool observation containing literal text like `User: John Doe` could be mistaken for a real dialogue turn; (3) loss of native tool semantics — Ollama preserves structured `role="tool"`/`tool_calls` objects, while Gemini's flattened string degrades them to plain text.

**Why this was off-target:** these are real findings, but about a *different* design decision than the one asked about — the flat-string *serialization strategy* (undocumented as an ADR at the time), not the *statelessness* decision from Q2 (ADR-0007). This distinction was clarified, and the serialization-strategy risk was recorded as new tracked debt in `CLAUDE.md` rather than discarded, since it names a real, previously untested failure scenario.

**Answer given (second attempt, redirected back to the original question):** Named the O(N²) cumulative-token-growth consequence directly: on Gemini, every turn resends the full prior transcript, so total tokens processed across an N-step agent run scale roughly as O(N²) rather than paying for the final context size once — a 10-step run pays for the early prefix 10 separate times, exhausting the free-tier Tokens-Per-Minute quota (or inflating billing) much faster than the raw context size would suggest. Additionally named WAN network transit and time-to-first-token overhead added on every step against a hosted API, contrasted with Ollama's zero-network-transit, zero-cost local calls.

**One claim flagged rather than accepted at face value:** the answer asserted Ollama's local inference engine "automatically reuses its in-memory KV cache for repeated prompt prefixes." This is plausible given how Ollama's runtime is documented to behave, but it was not something this project's own benchmark actually measured or verified — `OllamaLlmClient` sends the full message list fresh on every call too, with no explicit context/session threading back to Ollama's own internal state. Per Rule 9's spirit, this was named as "believed true, not verified here," not treated as a confirmed project finding.

**Detection method, supplied when the answer didn't name one:** `LlmResponse.inputTokens()`/`outputTokens()` already return on every call — instrumenting an agent loop to log those two numbers per step (with the correlation ID already available via `CorrelationIdFilter`) makes the O(N²) growth directly observable as a climbing number across turns, rather than a theoretical prediction. This is the concrete need behind Phase 14 (AI Governance/Compliance Observability) named earlier in this project.
