## Q1: Why use Testcontainers for the integration tests instead of pointing them at the already-running `docker-compose` Postgres instance?

**Answer given (first pass):** Framed around data-safety/pollution risk — correct, but incomplete, and included an imprecise "thread pool" resource-contention claim that didn't actually fit a project with no real user traffic yet.

**Accepted answer:** A persistent, already-migrated database would never re-validate that the migration file *itself* is correct — it would only prove the repository code works against whatever schema that database currently happens to have, which could be stale, hand-patched, or drifted from the actual migration scripts. Testcontainers starts from nothing every run, so the test is proving the full chain: the migration file is correct *and* the repository code works against exactly what that migration produces — not just the second half of that claim.

## Q2: Given `save`/`findById` have no `@Transactional` boundary, is that a gap — and if so, where would one actually be needed?

**Answer given (first pass):** Correctly concluded no `@Transactional` belongs on the *existing* methods, and correctly named future stock reservation (read-then-write) as the operation that will eventually need one. Initially justified the current lack of a boundary as "these methods don't need ACID," which is imprecise.

**Why "doesn't need ACID" was wrong:** every single SQL statement already gets full ACID guarantees from Postgres by default, with or without `@Transactional`. `@Transactional` isn't what supplies atomicity to a single statement — it's not doing anything a single statement doesn't already have.

**Accepted answer:** The real reason `save`/`findById` don't need `@Transactional` is that a single statement has nothing left to *compose* — `@Transactional` exists to bind multiple statements into one atomic unit, and there's only one statement here. A future `reserveStock`-style operation (read current quantity, decide, then write) is the first place with more than one statement to bind together — that's where the boundary actually becomes meaningful. Separately and explicitly noted: even a correct `@Transactional` boundary around that future method would **not** by itself prevent a concurrent lost-update/overselling race — that requires explicit locking or isolation-level reasoning, which is Phase 1's actual subject matter, not something to solve prematurely here.

## Q3: Why didn't the Spring Boot BOM catch the Testcontainers artifact rename (the version mismatch that caused a build failure)?

**Answer given:** Correctly identified the mechanism unprompted, on the first pass.

**Accepted answer:** A BOM (Bill of Materials) is an exact-coordinate lookup table — it maps a specific `groupId:artifactId` to a managed version, with no aliasing or rename history built in. When an artifact gets renamed (as Testcontainers' modules were, prefixed with `testcontainers-`), the *old* coordinate simply isn't a key in the BOM anymore — it's not that the BOM has the wrong version for it, it has no entry for it at all. This is categorically different from a version *conflict*, where the coordinate still exists in the BOM but multiple dependency sources disagree on which version should win.
