## Q1: `reingestFromSource` used to return `void`; now it returns `IngestionOutcome`. What specific, real operational blind spot did the `void` version create?

**Answer given (correct, no correction needed):** "With `void`, 'succeeded' was incremented on any normal return from `reingestFromSource`, regardless of whether it took the skip branch or the full re-ingest branch. An operator watching `succeeded=N, failed=0` genuinely cannot tell which happened. That's the actual blind spot."

---

## Q2: Walk through exactly why the `source_documents` hash upsert has to live inside the same `@Transactional` method as the chunk delete/insert, not as a separate call made just before it. Trace the specific failure sequence this prevents.

**Answer given (complete and correct, including the sharpest part unprompted):** traced the exact sequence — hash update as a hypothetical separate, immediately-committed call; then the transactional delete+insert begins; a chunk fails partway through embedding; Spring's proxy rolls back the delete and the successful inserts, but the earlier hash commit is untouched since it was never part of that transaction. End state: `dispute_documents` correctly retains the old chunks, but `source_documents.content_hash` already reflects the new content.

The critical extension, volunteered without prompting: **this isn't a one-run problem, it's self-perpetuating.** The next run reads the same unchanged-on-disk file, computes the same new hash again, compares it against the already-corrupted stored hash, finds a match, and skips — forever. The system can never self-heal from this without a human noticing, because the corrupted tracking state is internally consistent with what it keeps re-observing.

**No correction needed.** This is the single sharpest answer given across every interview in this project — correctly identifying that the bug isn't a transient inconsistency but a permanent, silent data-staleness trap.

---

## Q3: `CorrelationIdFilter`'s `correlationId` MDC key can't be reused for this job's run ID. State the precise mechanical reason.

**Answer given (correct, mechanical, not conceptual):** "CorrelationIdFilter's correlationId is created when a http request come. The filter is invoked for http requests only. The job run is not a http request. it is a cron based execution. so correlationIdFilter will never be invoked for this path."

**No correction needed.** Correctly identifies that a Servlet `Filter` only executes within the servlet container's request-handling pipeline — a `@Scheduled` method runs on a scheduler thread that never enters that pipeline, so the filter structurally has no opportunity to run, not merely a design choice to skip it.

## Q4: You kept the FK at `RESTRICT` instead of `CASCADE`. Trace concretely what a future "delete a source document and its chunks" feature has to do differently under each option, and why forcing the extra step is actually valuable.

**Answer given (exceptional):** Under `CASCADE`, the feature could be one line (`DELETE FROM source_documents WHERE id = ?`), with Postgres silently removing dependent chunks as an invisible side effect — the implementing class wouldn't even need to know chunks exist. Under `RESTRICT`, that same one-liner fails immediately with a real foreign-key-violation exception, forcing the developer to write:

```java
@Transactional
public void deleteSourceDocument(Long sourceDocumentId) {
    disputeDocumentRepository.deleteBySourceDocumentId(sourceDocumentId);
    sourceDocumentRepository.delete(sourceDocumentId);
}
```

"A reviewer reading `deleteSourceDocument` sees both operations right there — it's explicit that deleting a source document also destroys its embeddings. Under `CASCADE`, that exact same consequence is real but invisible from the call site... We've already measured this directly — real embedding calls run anywhere from ~27ms to ~1.8s per chunk depending on cold/warm state, against a real API, for real cost. `RESTRICT` means a developer who deletes a `source_documents` row without realizing chunks depend on it gets stopped immediately by a constraint violation, forced to consciously decide 'yes, I actually want to destroy this computed data' — rather than `CASCADE` silently doing it as an unexamined side effect."

**No correction needed.** Grounding the argument in real, previously-measured cost data from Milestone 7.2 rather than an abstract "explicitness is nice" principle is exactly the kind of cross-referencing a Staff-level answer makes.

## Q5: A bug in a newly-deployed `BoundedSentenceChunker` causes it to throw for every file in the corpus during one scheduled run. Walk through what an operator watching logs would see. Then: what's the real risk if nobody is watching, and what does this milestone's observability do and not protect against?

**Answer given (excellent overall conclusion, one factual imprecision):** correctly traced that the whole transaction (hash upsert + chunk delete) rolls back per file, leaving each document's data untouched; the per-file catch logs the real exception pointing directly at the faulty chunker code; this repeats for every file, `failedFiles` ends up containing all of them; the final summary and every per-file error line share one `ingestionRunId`, enabling correlated log queries.

On the harder half: "`run()` doesn't throw at the top level... There's no failed exit code, no crashed process, nothing for a process supervisor or Spring's scheduler to notice... **everything this milestone built is passive** — `ingestionRunId`, the structured summary counts, the per-file error logs — all of it is information made available in a well-correlated form, not a signal that reaches anyone. There's no metric emitted anywhere that could be graphed or threshold-alerted... no dead-man's-switch."

**One correction:** the claim that a total-failure night and a healthy, nothing-changed night produce "the exact same `succeeded=0` signal" is not quite right — they don't, in the full structured summary this milestone actually built. A healthy night produces `succeeded=0, skipped=N, failed=0`; the failure scenario produces `succeeded=0, skipped=0, failed=N` — genuinely distinguishable data, specifically because of this same milestone's `IngestionOutcome` fix. The real gap isn't that the data looks identical — it's that *nothing automatically reads and interprets the distinction*. A human glancing only at "did the process crash" would miss it; a human or system actually parsing `skippedCount` vs. `failedCount` would catch it immediately. This is a sharper version of the answer's own conclusion (observability ≠ alerting), not a contradiction of it.
