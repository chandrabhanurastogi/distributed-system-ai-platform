## Q1: The migration declares `embedding` as `vector(768)`. Phase 7's `VectorDimensionMismatchException` enforced dimension-matching at *runtime*, in Java. What does declaring it as `vector(768)` in the schema give you that a runtime check in application code cannot?

**Answer given (correct, complete, unprompted on both halves):** "A runtime check in application code is only as strong as 'every writer remembers to call it, and no one bypasses it.' A schema constraint isn't something you have to remember to call at all — it's a property of the data, checked by the one thing every writer is forced to go through.

What it deliberately does not give you, worth being precise about since this project doesn't let terminology get loose: `vector(768)` only guarantees count — 768 numbers, nothing about what they mean. A 768-dimensional vector from a totally different, incompatible embedding model would satisfy the column type just fine and insert without complaint, then silently produce meaningless-but-dimensionally-valid similarity scores."

**No correction needed.** The second half correctly re-derives, one layer down the stack, the exact same limitation Milestone 7.1's Q6 found for `VectorDimensionMismatchException` at the Java level.

## Q2: Walk through what actually happens, mechanically, when `ORDER BY embedding <=> CAST(:query AS vector)` runs against the 3 rows in the test, with no index on the table. Trace the actual execution.

**Answer given:** "The query is turned into a prepared statement parameter... pgvector will cast it to its own vector datatype before comparing... Postgres reads rows in physical storage order (heap order) — which happens to match insertion order here because nothing's been updated or vacuumed, but isn't guaranteed to match id order or any logical order in general. With no index, this is the only access path available — there's no structure to consult that could tell Postgres 'start near the closest rows and skip the rest.' [It computes] the cosine similarity by doing dot product divided by the magnitude... store that in memory and go to next row... until it traversed all rows and computed the score. Then it will sort them by distance in ascending order. A sort operation, whether it's Java's `Stream.sorted()` or Postgres's `Sort` node, is a stateful operation that requires its entire input before it can guarantee correct output — unless something upstream already hands it pre-ordered data. That's the general, transferable principle underneath both traces."

**One minor terminology correction:** `<=>` computes cosine **distance**, not cosine similarity (`distance = 1 - similarity`). The underlying dot-product-based computation described is the right shape; only the label was one step off.

**Noted as genuinely sophisticated, correct, and non-obvious:** the point about physical heap order not being a guaranteed logical order in general (it can diverge after `VACUUM` or updates) goes beyond what most engineers would think to mention. The generalization of "a sort needs its full input, whether `Stream.sorted()` or Postgres's `Sort` node" into one transferable principle directly extends the `BruteForceRetriever`/`Stream.sorted()` finding from Milestone 7.2's Q4 into a completely different execution environment.

## Q3: You already decided `vector_cosine_ops` over `vector_ip_ops`. In your own words, without re-reading the ADR — why is `vector_ip_ops` the *riskier* choice specifically for this corpus, even though it's mathematically equivalent for normalized vectors and cheaper to compute?

**Answer given (correct, well-targeted):** "This table isn't going to be written once and left alone. The same source documents will get re-chunked multiple different ways, and each chunking variant gets its own pass of embedding and insertion. That matters for the `vector_ip_ops` question specifically because 'someone has to guarantee unit-length forever' isn't a one-time cost paid at initial ingestion — it's a cost that has to be re-paid, correctly, on every single one of those repeated chunking/embedding passes."

**No correction needed.**

## Q4: This milestone deliberately has no repository class — the query runs via raw `NamedParameterJdbcTemplate` directly in the test. What's the actual bar for when a repository class earns its place, and why hasn't Milestone 8.1 crossed it?

**Answer given (first pass):** "A repository class earns its place once there's real domain/business logic — a second real caller — that needs to invoke the persistence operation, not just a test proving the SQL/schema mechanics work."

**Corrected:** pressed on whether "second" was the right count, given that *zero* real (non-test) callers currently exist for this SQL at all.

**Answer given (second pass — genuinely exceptional):** "A repository's entire reason to exist is to sit between domain logic and raw SQL... Look at what `OrderRepository` actually is: it takes and returns `Order` — a real domain object — and its two methods (`findById`, `save`) exist because `OrderService` (and presumably a controller above it) needs to call them. It wasn't written to wrap SQL in the abstract; it was written because a real domain object and a real caller both already existed.

Milestone 8.1 has neither... The one query that exists right now is called from exactly one place: the test itself, once, specifically to prove the extension/column/operator work. Wrapping that in a `DisputeDocumentRepository` today wouldn't decouple anything from anything...

There's also a real cost to introducing it early, not just an absent benefit: we don't yet know the right shape of that API. Should `topK`-style retrieval take a `double[]` or something else? Should it return a `Document`-equivalent domain type, or raw rows? Does `dispute_documents` even stay one table once Phase 8's stated goal of policy documents and scheme-rule documents in the same corpus gets built out, or does it need a discriminator column that reshapes every method's signature? Naming and shaping a repository API before any of that is decided means either guessing wrong and refactoring later, or over-designing now to hedge against guesses — both worse than waiting.

This is the same bar already applied twice in this exact repo... ADR-0006 explicitly rejected extracting `common` after two instances of duplicated code ('two small filter classes don't meet the bar')... and Milestone 7.2 rejected a 'swap for a vector DB later' interface around `BruteForceRetriever` for the identical reason...

So Milestone 8.1 staying at raw `NamedParameterJdbcTemplate` isn't an oversight or a shortcut — it's the same discipline this project has already named twice, applied a third time: the repository earns its place the moment real domain code needs one."

**No further correction needed.** Genuinely Staff-caliber synthesis — re-derived the principle by inspecting the actual codebase rather than reasoning abstractly, named a real, specific forward-looking cost (the corpus's eventual multi-category shape, correctly pulled from Phase 8's own stated plan), and cited ADR-0006's own language back accurately.

## Q5: If a future milestone added an HTTP endpoint that synchronously embedded and inserted a new dispute document within one request-response cycle — what specifically would go wrong under real load? Walk through the actual failure mode, not just "it would be slow."

**Answer given (excellent, three distinct correctly-reasoned mechanisms, all unprompted):**

1. **"Web server thread pool exhaustion."** Spring MVC's embedded Tomcat serves each request on a thread from a bounded worker pool. A synchronously blocking handler holds that thread for the entire embedding call. Requests arriving faster than the pool drains queue in Tomcat's accept queue; once that's full, new requests get connection-refused or time out, not a graceful error response.
2. **"The embedding backend is a shared, serialized resource, and it doesn't scale with request volume."** Ollama serving `nomic-embed-text` locally has limited real concurrency — inference effectively serializes requests behind it. Concurrent requests pile up waiting on the same engine, and "under queueing, wait time doesn't grow linearly with load, it diverges as you approach that engine's saturation point."
3. **"Database connection pool exhaustion, compounding on top."** If the natural instinct of wrapping "embed, then insert" in one `@Transactional` span is followed, the JDBC connection gets checked out *before* the embedding call starts and sits idle-but-held for the entire wait, even though the database is doing nothing during that time. With HikariCP's small default pool (~10), roughly 10 concurrent slow requests exhausts it — and "now unrelated endpoints on the same service that need a DB connection (a health check, a status lookup, anything else `dispute-service` might expose) start blocking or failing too, even though they have nothing to do with document ingestion."

**No correction needed.** Point 3 in particular directly re-applies the "blast radius" analytical pattern from Milestone 7.2's Q4 (one bad row failing an entire query, not just itself) to a completely different mechanism — shared-resource contention cascading to unrelated functionality.
