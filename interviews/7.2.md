## Q1: `BruteForceRetrieverTest` uses hand-crafted vectors with no Ollama involved; `BruteForceRetrievalIntegrationTest` uses real embeddings from real Ollama. What is each test actually proving that the other one cannot prove on its own?

**Answer given (attempt 1 — described *what*, not *why*):** "`BruteForceRetrieverTest` is testing the cosine similarity and top-k with hand-crafted corpus. It also tests different types of error handling. `BruteForceRetrievalIntegrationTest` is not a mocked unit test — a real, end-to-end retrieval pipeline test using the `nomic-embed-text` model from Ollama. It's doing real embedding and real ranking instead of a hand-crafted corpus."

**Pressed for the actual distinction:** why does that difference matter — why couldn't the integration test alone prove the ranking logic is bug-free, and why couldn't the unit test alone prove the real system works end-to-end?

**Answer given (attempt 2 — still missed the core point):** "`BruteForceRetrieverTest` does not have vectors of similar dimension as `BruteForceRetrievalIntegrationTest`. That makes it limited in testing scope for large corpus and larger dynamic vectors." (Dimensionality/corpus size were not actually the distinguishing factor — nothing prevents hand-crafting a 768-dimension vector, it's just tedious.)

**Taught directly, since two attempts had converged on adjacent-but-not-quite-right framings:** the real distinction is *certainty of the expected answer*. Hand-crafted vectors give you a mathematically certain expected outcome, computed by hand in advance — a failed assertion means, with zero ambiguity, that your own `BruteForceRetriever` logic is broken. Real embeddings give you no such ground truth — you only have an intuition about which cluster should score higher, not an exact provable number — which is exactly why the integration test deliberately asserts only "the top result is *some* distributed-systems document" rather than an exact full ranking. Conversely, the unit tests never call Ollama and could all be green while `OllamaEmbeddingService` is completely broken (wrong endpoint, wrong JSON field) — only the integration test proves the real wiring between a live external system and this code actually works, and only it says anything about the embedding model's real semantic quality. This is a general testing principle, not specific to this milestone: unit tests prove your own logic with certainty using controlled inputs; integration tests prove real-world composition and validate assumptions about systems you don't control. Neither substitutes for the other.

## Q2: You measured 14,308ms to embed 8 sentences, then immediately re-ran the identical test and got 217ms. Walk through exactly why that happened — and explain why reporting only the first number, or only the second number, would each have been a mistake for this milestone's write-up.

**Answer given (correct):** "Ollama had unloaded `nomic-embed-text` from memory after a period of inactivity since it was pulled, and the first call in this test run paid a real model-load cost before falling back to fast steady-state inference. Both numbers are kept, not just the fast one — cold-start latency distinct from steady-state latency is a genuine, real characteristic of locally-hosted (or on-demand/serverless) model serving, not an artifact to discard."

**Noted:** this answer was very close to a direct recall of this session's own prior explanation of the same finding — correct in substance, but worth being able to produce independently, not just reproduce.

**Supplementary check, to confirm genuine understanding rather than recitation:** why would a model-serving system deliberately unload an idle model at all, instead of keeping everything loaded forever?

**Answer given (in the human's own words, confirming real understanding):** "Keeping model in memory all the time would need more memory (RAM) which is expensive and not the best use of loaded model if it's not being used."

## Q3: Given the measured `nomic-embed-text` output is near-unit-length (`~0.9999998`), and that Milestone 7.1 covered that unit-normalized vectors make `dotProduct` and `cosineSimilarity` numerically identical — would you actually change `BruteForceRetriever` to use `dotProduct` instead of `cosineSimilarity`, to get that performance win? Why or why not?

**Answer given (excellent, staff-level reasoning):** "No — I wouldn't make that swap in `BruteForceRetriever`. The core problem: it converts an observed fact into an assumed invariant. `~0.9999998` is something this model, at this version, on this run happened to produce — not a contract Ollama or `nomic-embed-text` documents or guarantees. If the embedding model gets swapped..., vectors might stop being unit-length, and `dotProduct` would keep running — no exception, no crash — and silently return a different, wrong ranking that still looks like a plausible similarity score. That's the worst kind of bug this codebase can produce: not a loud failure, a quiet semantic one. Rule 4 is relevant here too — the moment you feed non-unit vectors into `dotProduct`, the number it returns isn't 'cosine similarity' anymore, and if the code still reports it as a similarity score, that's exactly the kind of loose terminology the project rules forbid.

It's also solving a cost that doesn't exist at this scale. The actual latency in this test is dominated by the HTTP round-trip to Ollama... The `sqrt` and division `cosineSimilarity` does on top of that is nanoseconds on an 8-document corpus — shaving it off buys nothing measurable here, and the milestone explicitly scoped performance work out (that's `pgvector`'s job).

The right way to capture the insight, if it ever mattered: don't opportunistically exploit an incidental property of one model's output. Make unit-length an enforced invariant at a boundary — e.g., normalize every vector explicitly when a `Document` is created (or assert magnitude ≈ 1 within a tolerance and fail loudly if violated) — and only then is `dotProduct` safe, because at that point your own code guarantees the precondition instead of borrowing it from Ollama's current behavior. That's exactly the real decision `pgvector` makes you name explicitly (`vector_cosine_ops` vs. `vector_ip_ops`...), which is worth resurfacing as a real decision when Phase 8 arrives, not something to smuggle into `BruteForceRetriever` now on the strength of one measurement.

So: keep `cosineSimilarity`. It's correct regardless of whether the input is normalized, it costs nothing at this corpus size, and it doesn't quietly bet the ranking's correctness on an external model's undocumented behavior."

**One factual correction:** the answer cited "~106 ms/sentence" for the HTTP round-trip cost. This doesn't match either real measured number — 27ms/sentence (warm re-run, 217ms ÷ 8) or 1,788ms/sentence (the cold-start-inclusive average). The conclusion was unaffected (both real numbers dwarf a nanosecond-scale arithmetic operation), but the specific figure was a misremembered approximation rather than the actual logged value — worth flagging precisely, since Rule 9 applies to *citing* a previously-measured number correctly, not only to producing one honestly the first time.

## Q4: Suppose a later milestone swaps `nomic-embed-text` for a different embedding model with a different dimensionality (say 1024), and the migration is done carelessly — half the corpus re-embedded, half still 768-dimension, and a new query comes in embedded with the new model. Trace *exactly* what happens when `BruteForceRetriever.topK` runs against that mixed corpus: does it crash, and where, or does it silently produce a wrong result for part of the corpus?

**Answer given (excellent, precise trace, the strongest single answer in this project's interviews so far):** "It crashes, it does not silently degrade. `VectorMath.cosineSimilarity(queryVector, doc.embedding())` gets invoked once per document, in the corpus `List`'s encounter order, unconditionally — before sorting, before `limit(k)` even matters.

Each call goes into `cosineSimilarity` → `validatePair(a, b)`, which checks `a.length != b.length` and throws `VectorDimensionMismatchException`... Here `a` is `queryVector` (1024-dim, new model) and `b` is `doc.embedding()`. The exception fires on the first document in the corpus's list-iteration order whose embedding length isn't 1024 — the first stale 768-dim document the stream happens to reach, purely by position, with no regard to which documents would've actually ranked well.

The blast radius is the entire call, not 'half the corpus.' This is the counterintuitive part: because `.sorted()` can't emit anything until it has consumed the whole source, `limit(k)` downstream doesn't save you — even if the top-2 winners by position happen to be two freshly-re-embedded 1024-dim documents that come first in the list, the pipeline still has to walk every remaining document to build the sort buffer, and it will hit a stale 768-dim document somewhere in that walk (unless literally 100% of the corpus was migrated).

Which documents 'cause' the crash: whichever stale document sits first in iteration order — arbitrary, migration-order-dependent, not deterministic across different corpus orderings. Which documents are 'affected': every document, and every caller of `topK` for that query. There is no partial result.

Is that good or bad? It's fail-fast, which is better than the alternative failure mode from your last question: nothing here computes a wrong similarity score for a mismatched pair — dimension mismatch is checked before any math runs. But it's a blunt fail-fast: the exception carries expected/actual lengths but no document id, no count of how many rows are affected, and it kills 100% of that query's retrieval rather than isolating or flagging the stale subset. In a real system, one carelessly-skipped re-embed during a migration turns into a full retrieval outage on the next query that happens to touch that row, not a degraded/partial result you'd notice gradually.

That gap — no dimension tagging on `Document`, no migration-safety check before a corpus is queried — is exactly the kind of thing worth a line in `ARCHITECTURE.md`'s known-debt or a forward-looking note for Phase 8 once a real vector store with schema enforcement is on the table, rather than solving it now inside `BruteForceRetriever`, which was explicitly scoped to a tiny, single-model, in-memory corpus."

**No correction needed.** This answer correctly identified a genuinely subtle Java Streams fact (`.sorted()` is a stateful operation that defeats `.limit(k)`'s short-circuiting), correctly derived the non-obvious consequence (full-query failure, not partial), and correctly scoped the finding as tracked debt rather than something to fix inside this milestone's deliberately narrow scope. Recorded in `CLAUDE.md` → Known Existing Debt as a direct result of this answer.
