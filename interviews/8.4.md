## Q1: Why does classification need `temperature: 0.0`, specifically? (reconstructed from summary)

**Answer given (correct):** temperature is what gives the model a consistent decision
on the same input. Before `temperature` was set to `0`, `ClaimClassificationServiceTest`
was run against the exact same claim text on separate runs and produced different
reason codes across runs (`13.1` on one run, `10.4` on another) — a real, observed
non-determinism, not a hypothetical one, which is why classification specifically
(as opposed to open-ended chat) needs sampling effectively disabled.

**No correction needed.**

## Q3: What's the general, transferable principle for when to share vs. duplicate — beyond the specific `LlmClient` decision `ADR-0011` just made? (reconstructed from summary)

**Answer given (excellent — a sharper generalization than `ADR-0011`'s own framing):**
"The distinguishing principle: whether a genuine interface/implementation split already
exists. Embedding never had one... LLM-calling already had that split... So the real
rule isn't 'share once enough services need it' — it's 'if there's no seam, count
consumers; if there is a seam, share the stable side and keep duplicating the risky,
specific side, independent of the count.'"

**Validated as correct, with one precision refinement added:** "counting consumers
stops being the right question" slightly overstates it — count is still what
*triggers* the question (a second real consumer was still required to raise it at
all, same trigger as the embedding case). What actually changes is the *threshold*:
a stable, behavior-free interface clears the bar at two consumers because sharing it
costs nearly nothing, while `ADR-0006`'s three-instance bar was calibrated for the real
cost of duplicated, mutable *logic* that can drift. Same trigger, different bar,
because the two things being judged (an interface vs. an implementation) carry
different risk. The core insight — judge the interface and the implementation
separately, rather than as one undifferentiated "capability" — is exactly right, and
is a genuine generalization beyond what `ADR-0011` itself states.

## Q4: Trace what would (and would not) need to change if `dispute-service` switched its classification LLM call from Ollama to Gemini. (asked after compaction; transcribed verbatim)

This question was first asked with a stale premise — it assumed `OllamaChatRequest`/
`OllamaChatResponse` still used `common.llm.ChatMessage` directly as their Jackson wire
type. The human caught this immediately ("I don't think that's the case anymore. can
you double check?"), which was correct: the `OllamaMessage` wire-format fix (see
addendum to `ADR-0011`) had already landed. The question was revised in place to ask
about a provider switch instead, given the fix was now real.

**Answer given, part 1 — what would change (correct and complete):**
1. New `dispute-service`-owned files: a `GeminiLlmClient` implementing
   `common.llm.LlmClient`, plus Gemini-specific wire DTOs (Gemini's real API takes a
   flat string, not a messages array, so this needs its own flattening logic, not
   `OllamaMessage`) — deliberately not a dependency on `llm-fundamentals`'s
   `GeminiLlmClient`, per `ADR-0011`'s already-established reasoning (avoids the
   cross-service coupling and the tracked `serializeMessages()` bug).
2. New config: `gemini.base-url`, `gemini.api-key`, `gemini.model`, plus a new
   `llm.provider` property `dispute-service` doesn't currently have at all.
3. **Bean disambiguation** — the sharpest part of the answer: once two `LlmClient`
   implementations exist in the same Spring context, `ClaimClassificationService`'s
   constructor injection of a bare `LlmClient` becomes ambiguous and Spring fails at
   startup. Needs `@ConditionalOnProperty` on each implementation, mirroring
   `llm-fundamentals`'s exact existing pattern (and its `LlmProviderConditionTest`,
   worth mirroring too).
4. New tests for the Gemini client itself.

**Answer given, part 2 — what would not change, after being asked directly for it
(correct and complete):** the `common.llm` interface trio; `ClaimClassificationService`
(depends on the interface, never a concrete type by name); `ClassificationResult`; the
entire embedding/chunking/retrieval/scheduling stack (unrelated concern); the existing
`OllamaLlmClient`/`OllamaChatRequest`/`OllamaChatResponse`/`OllamaMessage` files
(become the inactive provider, exactly like `llm-fundamentals` already runs both side
by side today); both existing test classes (exercise the service through the
interface, never referencing which provider is active).

**Self-correction, volunteered without being asked again — the standout moment of this
answer:** the human then challenged the assistant's own framing of the question,
which had asked "why the boundary you just fixed [`OllamaMessage`] is what makes that
list short." That framing conflated two distinct boundaries. The correction, given in
two passes:

- *First pass:* adding Gemini was always going to need its own wire DTOs regardless of
  the `OllamaMessage` fix, since Gemini's flat-string shape is nothing like Ollama's —
  a new Gemini client was never going to reuse `OllamaChatRequest` either way. The fix
  doesn't shrink this particular migration's file list at all; that shrinkage is
  entirely the `LlmClient` interface seam's doing (`ADR-0011`), not the wire-format
  fix.
- *Second pass, after the assistant conceded the first correction and asked what the
  fix* does *buy:* "What the fix actually buys is a guarantee, not a smaller diff:
  because `OllamaChatRequest.messages` is `List<OllamaMessage>` and not
  `List<ChatMessage>` anymore, adding (or later changing) a Gemini implementation can
  never, even accidentally, alter what `OllamaLlmClient` sends over the wire — there's
  no shared mutable surface between the two providers' wire formats. Without the fix,
  every time someone touched `ChatMessage` for Gemini's sake, they'd need to go
  re-verify Ollama's behavior hadn't silently shifted too... With the fix, that
  verification step doesn't need to exist at all, because it's structurally impossible
  for Gemini's needs to reach Ollama's wire format." Summarized in one line: **"provably
  untouched, not just untouched today by luck."**

**No correction needed on the final answer.** This is a more precise articulation than
the assistant's own attempt at the same point (which reached for a concrete example —
a hypothetical `tool_calls` field — rather than naming the actual property). The
distinction between an invariant that holds because nothing has broken it yet and one
the compiler makes structurally impossible to break is a genuinely transferable
architectural instinct, not specific to this case.
