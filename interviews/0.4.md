## Q1: Why does a `@Transactional` boundary around `reserve` not prevent two concurrent requests from overselling the same SKU? Walk through the actual interleaving.

**Answer given (first pass):** Correct in conclusion (pessimistic locking is needed) but described the race vaguely — "threads may commit at the same time."

**Answer given (second pass, after being asked for a concrete step-by-step trace):** Correctly identified that both transactions read the pre-update quantity *before either one writes* — so both proceed believing they're operating on the same original value. Beyond what was asked, an important point was volunteered unprompted: with the current unconditional `UPDATE`, the overwrite is **silent** — neither caller gets an exception, both get `200 OK`, and the resulting database value can look entirely plausible (not negative, not obviously wrong) even though the real business fact — who actually holds a valid reservation — is now incorrect.

**What happened next, worth recording as part of the answer:** this directly triggered a live test of the project's own plan. The human asked to implement pessimistic locking immediately to fix what had just been traced. This was named as a direct conflict with Phase 1's design (the bug is deliberately left in per ADR-0005, as a real baseline for a future concurrency experiment). The human chose to stay on the original plan rather than fix it early — the strongest possible confirmation that leaving the bug in place was the right call, since it survived contact with the actual temptation to "just fix it now."

**Accepted answer:** A `@Transactional` boundary guarantees that a *single* transaction's own multiple statements commit or roll back together. It says nothing about what happens when *two separate* transactions both read the same pre-update value before either writes — that's a lost-update race, and preventing it requires either pessimistic locking (block the second reader until the first writer commits) or optimistic locking (detect the conflict at write time and reject/retry) — mechanisms `@Transactional` alone does not provide.

## Q2: Why is `findBySku` a new repository method rather than reusing `findById` with a lookup/translation layer somewhere else?

**Answer given (first pass):** Reached for general software-engineering virtues — coupling, extensibility — rather than the specific mechanical reason.

**Accepted answer:** The two methods query fundamentally different columns (`id` vs. `sku`). A translation layer sitting in front of `findById` would need to run the equivalent of `findBySku` internally anyway, just to convert a SKU into an `id` first — making the design strictly *more* expensive (two queries instead of one) without actually gaining any real decoupling. There's no coupling being avoided; there's just an extra hop being added.

**Worth recording:** during this discussion, the human independently noticed that `findById` is now unused by any production code path — a genuinely good catch. Correctly left alone rather than removed, since it's still exercised by Milestone 0.3's own test suite and the roadmap had already committed to not touching Milestone 0.3's repository code in this milestone.

## Q3: What's the actual difference between a 404 (order not found) and a 409 (insufficient stock) in HTTP semantics — why isn't insufficient stock also a 404, or a 400?

**Answer given:** Correctly explained 404, and added a good unprompted business framing: 409 signals "needs restocking," 404 signals "doesn't exist." Did not directly address why not 400.

**Accepted answer:** Per RFC 9110's actual distinction — 400 means the request is intrinsically invalid regardless of any server state, and is checkable with zero database access (which is exactly why quantity validation runs *before* the SKU lookup in this code: a non-positive quantity is wrong no matter what's in the database). 409 means a well-formed, valid request conflicts with the server's *current* state, and could succeed unchanged later if that state changes (more stock arrives). Insufficient stock is a 409, not a 400, precisely because the request itself was fine — the world just doesn't currently support it.
