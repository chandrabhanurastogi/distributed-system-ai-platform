## Q1: What is cosine similarity actually measuring geometrically, and why does the formula deliberately divide out vector magnitude rather than just using the raw dot product as the similarity score?

**Answer given (correct, no correction needed):** "Cosine similarity measures the angle between two vectors, ignoring their length. With only dot product, the longer vectors naturally get huge dot product scores, even if they are less relevant."

## Q2: Walk through exactly what happens, step by step, when `cosineSimilarity(a, b)` is called with `a = {1.0, 2.0}` and `b = {}` — an empty array. Which of your three exceptions fires, and why, tracing through the actual order of checks in your code?

**Answer given (correct):** `cosineSimilarity` calls `validatePair`. First both vectors are checked for null and pass. The second check is for length, where `b` fails, resulting in `EmptyVectorException`.

**Confirmed as complete:** dimension mismatch is also technically true here (`2 != 0`), but the empty-check fires first specifically because of the precedence order deliberately built into `validatePair` — the answer correctly identified `EmptyVectorException`, not `VectorDimensionMismatchException`, as the actual behavior, not just the theoretically-possible one.

## Q3: Your zero-vector check uses exact floating-point equality: `magA == 0.0`. Describe one realistic way a real embedding vector — not a hand-constructed test case — could end up with a magnitude extremely close to zero but not exactly zero. Then trace what your current code would actually do in that scenario.

**Answer given (correct and appropriately deep):** "In real ML/AI pipelines, vectors produced by embedding models or upstream pooling bugs rarely end up as exact `0.000...`. Instead, numerical inaccuracies or corrupted embeddings can result in astronomically tiny numbers (for example: `1e-300`). It would pass all checks and go to the cosine similarity formula, and it may produce an enormous value or `Double.POSITIVE_INFINITY` / `Double.NaN`."

**One additional layer of precision offered, not required to pass:** the failure could occur even later than described — `magA` and `magB` might each individually pass the `== 0.0` check (each a tiny but distinct nonzero double), yet their *product*, `magA * magB`, could itself underflow to exactly `0.0` during the multiplication — meaning the actual division-by-zero could happen without either input magnitude alone ever being flagged.

## Q4: Suppose an embedding model always normalizes its output vectors to unit length. What is the relationship between `dotProduct(a, b)` and `cosineSimilarity(a, b)` for vectors from that model? And why might a real production vector database default to raw dot product instead of cosine similarity as a performance optimization, given that relationship?

**Answer given (first half):** "Then dotProduct become identical with cosineSimilarity." Correct — when both vectors are unit-normalized, `cosineSimilarity(a,b) = dotProduct(a,b) / (1.0 * 1.0) = dotProduct(a,b)`.

**Second half — initially left unanswered, asked again directly:** "Because it avoids computing the magnitude and with large vector the computation of vector may be costly." Correct — precomputing normalization once at ingestion means every query-time comparison skips the `sqrt`/division work entirely, a real saving at the scale a production vector database operates on (potentially millions of comparisons per query).

## Q5: Your `cosineSimilarity` is a single O(1)-per-pair comparison. If a corpus grows to millions of documents, what's the time complexity of finding the top-5 most similar using brute force, and why does that fail to scale? Name the actual class of solution real vector databases use instead, and its fundamental trade-off.

**Answer given:** "I don't know this one. Please you help me on this."

**Taught directly rather than probed further, since this was genuinely new material:** brute-force comparison against every stored vector is `O(N)` per query (`O(N × d)` including dimensionality, but `N` is what dominates scaling). Real vector databases (including `pgvector`, which this project will use in Phase 8) use Approximate Nearest Neighbor (ANN) indexes — HNSW (a multi-layer navigable graph) or IVFFlat (cluster-based partitioning) — to touch only a small subset of the corpus per query instead of all of it. The fundamental trade-off is speed vs. recall: because only part of the search space gets explored, the true single-best match can occasionally be missed, returning the 2nd- or 6th-best result instead of the actual best — a deliberate, tunable trade against exhaustive correctness in exchange for orders-of-magnitude faster queries.

## Q6: Suppose a corpus is embedded with Model A (384 dimensions) and later a query is embedded with Model B, which coincidentally also produces 384-dimension vectors. Your dimension check would pass. Would `cosineSimilarity` correctly detect that something is wrong? Why or why not — what invariant does your check actually verify, versus what it does *not* verify?

**Answer given (first pass — right intuition, didn't commit to a direct answer):** "Two different models will have two different numeric representation for same text so the embedding might be different that will result in incorrect cosine similarity."

**Pressed for the explicit yes/no the question actually asked:** `VectorDimensionMismatchException` checks exactly one thing — `a.length != b.length`, a purely structural check on array size. It has no way to know whether two `double[]` arrays came from the same embedding model or compatible coordinate spaces, since a `double[]` carries no metadata about its origin.

**Accepted answer:** No, the code would not detect anything wrong in this scenario. `cosineSimilarity` would run to completion and return some plausible-looking number between `-1` and `1`, with no exception and no warning that the result is meaningless — a more dangerous failure mode than a crash, since a silently-wrong-but-plausible number can flow through an entire system (search ranking, RAG retrieval) unnoticed.
