## Organic corrections during implementation (before the formal interview)

Worth recording alongside the formal questions, not instead of them:
- The `tools`/`tool_calls`/`function` terminology needed a full concrete walkthrough before it landed — this wasn't obvious from the API shape alone.
- **MCP conflation, caught and corrected:** tool-calling was initially conflated with MCP (Model Context Protocol). They are not the same thing — see Q-equivalent below for the accepted distinction.
- **"The LLM is assumed tested" — named as factually wrong.** The initial justification for trusting `llama3.2`'s tool-calling reliability was "the LLM is assumed tested, like real IT companies do." This was corrected: a model provider testing general capability says nothing about whether *this specific* tool schema and prompt combination works reliably in *this* application. This is precisely why Phase 13 (Evals) exists in this project's roadmap — to measure tool-usage accuracy rather than assume it.

---

## Q1: Why does a tool call's `arguments` field arrive as a real, parsed JSON object, while structured output's `content` field arrives as a plain string that needs a second parse?

**Answer given (first pass):** Explained why `content` is *empty* during a tool call — a true fact, but it answers a different question ("why is content empty") than the one asked ("why is arguments already parsed").

**Accepted answer (reached on the second attempt):** Structured output never leaves "raw model-generated text" territory — the model is just generating text that happens to be *shaped* like JSON, and the caller has to parse that text themselves. Tool-calling is different: Ollama's own server-side code recognizes the model's tool-call signal and extracts it into a real, structured object *before* it ever reaches the caller. The asymmetry isn't arbitrary — it reflects two genuinely different mechanisms, not just two different response formats for the same thing.

---

## Q2: Does one passing test prove `llama3.2`'s tool-calling is reliable?

**Answer given:** Correctly rejected the premise — no, one test is not a reliability claim — and correctly identified that repeated testing is what would actually establish it. This was real growth from the same milestone's earlier "the LLM is assumed tested" starting position.

**Sharpened with two additional precision points, on further questioning:**
1. Repetition matters specifically *because* generation is non-deterministic — identical input can produce a different output on a different run, unlike a deterministic function where one passing test genuinely does prove the case.
2. The actual measurement that matters is a success *rate* over varied prompts and scenarios, not the identical single case repeated over and over — exactly the shape of metric this project's Phase 13 (Evals) already names: tool-selection accuracy, argument accuracy, execution success rate.

---

## Clarification: is tool-calling the same thing as MCP?

**Accepted answer:** No. Tool-calling is a feature of the chat API itself — one request, one model, the caller's own code executes the function directly. MCP (Phase 11 in this project) is a separate client-server protocol with its own transport and capability negotiation; it *uses* tool-calling as one of its underlying mechanisms, but is not the same thing — the same way one HTTP request isn't "REST" by itself.
